# Trace Descriptions – Phase II (Member 4)

**Project 7: 2-Way Set-Associative Cache with LRU vs Direct-Mapped Baseline**
**Owner: Member 4 – Traces, Charts, and Regression**

This document explains all 11 deterministic traces used in Phase II of the evaluation.
Each trace is designed to isolate a specific locality pattern or cache-behaviour scenario.
All traces are generated by `scripts/gen_traces.py` and processed by `tb/tb_compare.v`.

## Detailed Trace Descriptions

### T1: Sequential Stream (`seq_stream.txt`) – 256 accesses

**Access Pattern:** 256 consecutive word reads at stride = 4 bytes,
addresses `0x0000` to `0x03FC` (1 KB total, one pass).

**Locality Modelled:** Pure spatial locality, zero temporal reuse.

**Expected Result Before Running:**
Each 16-byte block holds 4 words. The first word in each block misses (compulsory);
the next three words in the same block hit. This gives exactly 192 hits / 64 misses = **75.00%**
for both caches, since a single sequential pass creates no index conflicts.

**Purpose:** Establishes the spatial-locality baseline and confirms the 4-word block pipeline
behaves correctly on both designs.

---

### T2: Small Loop (`small_loop.txt`) – 640 accesses

**Access Pattern:** 64 words (256 bytes) at addresses `0x0400`–`0x04FC`,
looped 10 times.

**Locality Modelled:** Strong temporal and spatial locality. Working set = 256 B =
16 cache blocks, well within the 1 KB cache.

**Expected Result Before Running:**
Iteration 1: 16 cold misses, 48 hits (hits within fetched block). Iterations 2–10: 100%
hits (all blocks resident). Overall hit rate = (640 − 16) / 640 = **97.50%** for both caches.

**Purpose:** Demonstrates the core temporal-locality benefit of caching for loop-dominated code.

---

### T3: Ping-Pong Conflict (`pingpong.txt`) – 200 accesses

**Access Pattern:** Alternating reads between two addresses:
- Addr A: `0x0020` → Direct-Mapped Line 2, Tag 0; 2-Way Set 2, Tag 0
- Addr B: `0x0420` → Direct-Mapped Line 2, Tag 1; 2-Way Set 2, Tag 2

**Locality Modelled:** Temporal reuse of two blocks that map to the same set/line.

**Expected Result Before Running:**
- **2-Way LRU:** Both blocks fit in Way 0 and Way 1 of Set 2. After 2 cold misses,
  all 198 remaining accesses hit. Hit rate: **99.00%**.
- **Direct-Mapped:** Only one line available. Each access evicts the other → complete
  thrashing. Hit rate: **0.00%**. Total cycles: ~6.6× worse.

**Purpose:** The canonical demonstration of why associativity exists. A 2-way cache eliminates
all conflict misses; the direct-mapped baseline cannot hold both blocks simultaneously.

---

### T4: 3-Way Cyclic Conflict (`cyclic3.txt`) – 300 accesses

**Access Pattern:** Three addresses mapping to the same set, cycled as A→B→C→A→B→C…:
- `0x0030` (Set 3, Tag 0), `0x0430` (Set 3, Tag 2), `0x0830` (Set 3, Tag 4)

**Locality Modelled:** Working set larger than the associativity of the target set.

**Expected Result Before Running:**
- **Direct-Mapped:** Complete thrashing, 0% after cold misses.
- **2-Way LRU:** The LRU way always holds the block used longest ago, which is exactly the
  block needed next in the cycle. Every access is a miss after cold start. Hit rate: **0.00%**.

**Purpose:** Demonstrates the **LRU pathological case**: N+1 blocks cycling through an N-way
set defeats LRU completely. Despite spending extra hardware on associativity, the 2-way cache
performs identically to the direct-mapped baseline here.

---

### T5: Strided Access (`strided.txt`) – 256 accesses

**Access Pattern:** Reads at 64-byte intervals (stride = 64 B = 4 blocks),
covering 256 addresses (16 KB range).

**Locality Modelled:** Spatial locality with large stride; each block is used once then abandoned.

**Expected Result Before Running:**
Stride of 64B means every access lands in a different cache set (mod 64 unique set indices).
With 32 sets in both caches, the access pattern wraps around without conflict. Expected hit rate
is **~75%** (3 of 4 words hit within each fetched block after the first word miss).
Both caches behave identically.

**Purpose:** Verifies that large-stride access behaves like sequential access when the stride
doesn't create index aliasing. Confirms spatial locality benefit holds across both architectures.

---

### T6: Uniform Random (`random.txt`) – 300 accesses

**Access Pattern:** 300 uniformly distributed random read addresses (seed 42, word-aligned).

**Locality Modelled:** No locality. Each access is independent.

**Expected Result Before Running:**
With a 1 KB cache (64 blocks) and a 16 KB address space (1024 possible blocks), the probability
that any given access hits the cache is roughly 64/1024 = 6.25% at the start, rising slowly as
blocks warm up. Expected hit rate in the **25–35%** range, similar for both caches.

**Purpose:** Provides a worst-case locality baseline. Random accesses show that caching provides
limited benefit when there is no reuse.

---

### T7: Mixed Read/Write (`mixed_rw.txt`) – 400 accesses

**Access Pattern:** 400 accesses over a 128-byte hot region, randomly 70% reads and 30% writes
(seed 7).

**Locality Modelled:** Temporal reuse with write pressure under write-through policy.

**Expected Result Before Running:**
The 128-byte working set fits in 8 blocks, well within the cache. Reads after the initial cold
misses hit (~87% read hit rate). Writes always go to memory (write-through), so each write costs
WR_LAT = 4 cycles regardless of cache state. The 103 write accesses each stall for 4 cycles.
Both caches behave nearly identically.

**Purpose:** Isolates the write-through cost. Demonstrates that frequent writes are expensive
even when the working set fits in cache, because write-through sends every write to main memory.

---

### T8: Large Loop (`large_loop.txt`) – 384 accesses

**Access Pattern:** 96 consecutive words (384 bytes), then loop = 4 iterations total =
384 accesses covering 384 B, but the trace accesses 96 unique blocks × 16 B = **1,536 bytes**
of data, which exceeds the 1 KB cache capacity.

**Locality Modelled:** Capacity miss scenario. Working set slightly exceeds cache.

**Expected Result Before Running:**
- **Direct-Mapped:** 96 blocks mod 64 sets = 32 sets get 1 block, 32 sets get 2 blocks.
  The 32 sets with 2 mappings conflict-miss on later iterations, but the 32 sets with 1 mapping
  hit. Net hit rate ≈ **25%**.
- **2-Way LRU:** With 32 sets × 2 ways, the cache can hold 64 blocks. The 96-block working set
  means every set is contested, and LRU evicts needed blocks before reuse. Hit rate ≈ **0%**.

**Purpose:** Shows that more associativity is NOT always better. When the working set
exceeds cache capacity, direct-mapped can outperform 2-way LRU due to its different eviction pattern.
This is an honest, counter-intuitive result that must be reported accurately.

---

### T9: Hot Stream (`hot_stream.txt`) – 400 accesses

**Access Pattern:** 400 accesses: 70% reads from a 128-byte hot region (seed 13 randomised),
30% reads sweeping sequentially through a cold 2 KB region.

**Locality Modelled:** Bimodal locality. Hot frequently-accessed working set + cold sweep.

**Expected Result Before Running:**
The hot region (8 blocks) stays resident since it is accessed 2.3× more frequently than it is
evicted. The cold sweep adds compulsory misses per new block accessed. Expected hit rate is
**moderate (~40–60%)** for both caches, slightly favouring 2-way (fewer conflicts in hot region
index positions).

**Purpose:** Models a realistic server-like access pattern where a small hot dataset receives
most traffic but occasional cold sweeps (e.g., bulk data, logging) perturb cache state.

---

### T10: Matrix Walk (`matrix_walk.txt`) – 512 accesses (Phase II)

**Access Pattern:** A 16×16 word matrix (256 words = 1 KB) stored in row-major order at
base `0x1000`. Phase A traverses row-major (stride = 4B); Phase B traverses column-major
(stride = 64B per column step).

**Locality Modelled:**
- Phase A (row-major): high spatial locality — accesses move through contiguous words.
- Phase B (column-major): poor spatial locality — each column step skips 64 bytes,
  landing in a different cache block each time.

**Expected Result Before Running:**
- **Phase A (row-major, 256 accesses):** All blocks warm during first row. Subsequent rows
  hit 3/4 words per block. Expected hit rate ≈ **75%** for both.
- **Phase B (column-major, 256 accesses):** All 256 blocks have been evicted between rows
  since the matrix (1 KB) exactly fills the cache. Column-major reloads blocks row-by-row
  with minimal hit rate. Direct-mapped may suffer extra conflict misses when two columns share
  the same set index (columns 0 and 8, offset by 512B = 32 sets × 16B).
- **Overall hit rate (both phases):** ~37.5% (derived from 75% phase A, ~0% phase B).

**Purpose:** Demonstrates that two programs accessing the **same data** can experience very
different cache performance depending only on the order of access. This is a practical insight
for memory-bound code (e.g., matrix multiplication: always use row-major).

---

### T11: Write Heavy (`write_heavy.txt`) – ~640 accesses (Phase II)

**Access Pattern:** A 512-byte working set (128 words at `0x0800`) accessed 5 times.
Each access is independently randomised (seed 99): 80% writes, 20% reads.

**Locality Modelled:** Write-intensive workload under write-through no-write-allocate policy.

**Expected Result Before Running:**
- **Write misses (no-write-allocate):** A write to a block not in cache is sent directly to
  main memory without loading the block. No cache line is allocated. This means subsequent
  writes to the same address also miss until a read brings the block in.
- **Read hits (after a read miss loads block):** Once a block is loaded on a read miss,
  subsequent reads to the same block hit.
- **Cycle cost:** Each write costs WR_LAT = 4 cycles regardless of hit/miss. With ~80% writes
  (~512 operations), write cycles dominate the total cycle count.
- **Expected hit rate:** Low overall (write-driven), since most writes never fill the cache.
  Both caches behave nearly identically here.

**Purpose:** Isolates the cost and behaviour of the write-through no-write-allocate policy.
Shows that for write-heavy workloads, the choice between 2-way and direct-mapped matters far
less than the write policy itself.
